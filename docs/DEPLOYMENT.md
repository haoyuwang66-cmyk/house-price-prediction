1. In production, I would use explicit model versioning combined with metadata tracking to manage different model versions. Each trained model would be saved with a unique version identifier (e.g. ml/model_v20260121174203.joblib), with a metadata file (e.g. ml/metadata_v20260121174203.json) that records essential information such as feature list etc. This ensures that every deployed model is reproducible and traceable.

2. For the API service, I would mainly monitor the latency of the API, CPU and memory used to make sure the service responds within an acceptable response time and remains reliable. In addition, I would track the number of errors, especially 4xx and 5xx responses, as well as the overall error rate, to quickly identify issues related to invalid requests or service failures. For the prediction model, I would focus on model quality metrics. This includes monitoring metrics such as Mean Squared Error (MSE) to evaluate prediction accuracy

3. Every trained model will be automatically saved with a unique identifier as its name, ensuring that all historical models are preserved. The version of the model that is currently deployed is specified in app/config.py. To roll back to a previous version, users can simply update the model path in app/config.py to point to the desired model file, and redeploy the API. This approach allows for a fast and safe rollback without retraining, as all previous model artifacts are preserved and can be used directly.
